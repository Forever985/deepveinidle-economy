3. WebSocket 游戏协议（核心）

3.1 握手与鉴权

GET /ws HTTP/1.1
Host: deepveinidle.com
Upgrade: websocket
Cookie: sid=bHb...cUA          ← 必须携带有效会话

→ HTTP/1.1 101 Switching Protocols
→ 无 Cookie 时：HTTP/1.1 401 Unauthorized（连接被直接拒绝）

3.2 帧格式

文本帧，纯 JSON，无压缩、无二进制。但服务端会把大帧做 WebSocket 分片（continuation 帧），客户端必须拼帧——这是实现时最容易踩的坑。

// 服务端 → 客户端：世界增量帧
{"tick": 39322008, "m": [ ...消息数组... ], "a": 3}

// 客户端 → 服务端：单条指令
{"t": "moveTo", "x": 188, "y": 78}
字段含义
tick服务器逻辑帧号，单调递增，1 帧 ≈ 0.6 s
m本帧消息数组，可空
a可选。确认序号——客户端发第 N 条指令后，服务端在帧里回 a:N 表示已处理（实测连续 a:1 … a:5 一一对应）

3.3 关键指令实测

发送返回
{"t":"resync"}两帧：welcome（323 KB 全量世界）+ snapshot（本人完整存档）
{"t":"ping","n":1}{"t":"pong","n":1}，用于 RTT 测量
{"t":"leaderboard"}22 个榜单 × 各 20 名（总榜/总经验/战斗/财富/收集 + 16 项技能榜）

3.5 实时增量消息类型

实测 12 秒内收到的核心消息类型：

类型含义
enter / leave玩家进出视野（带 id、name、x、y、gear、mount、work）
move移动：目标坐标 + 完整路径点数组 + speed
work当前作业：{siteId, tool:"pickaxe"|"rod"|"hammer"…, item}
batch产出结算：{kind:"produced", jobId, itemId, xp, tier, wire}
chat聊天：name / text / tick / channel / c 字段
leaderboard / marketStock / guildBoard / patronsBoard按需拉取的大块数据
架构判断：服务器只广播视野内的玩家动作（消息里反复出现 id 618 / 4960 / 200,83 附近聚集），并做了 actor 级增量——同一玩家的 work 状态反复推送 null 表示"未变化"。这是典型的 AOI（Area of Interest）裁剪 + 增量同步，长连接成本被压得很低。

4. 客户端实现要点

  • 必须先拿 cookie：POST /api/guest 或 /api/login，否则 /ws 直接 401。
  • 必须拼 WebSocket 分片：大帧（welcome / snapshot / leaderboard）会被拆成 continuation 帧，按 opcode 0x0 续接、看 FIN 位收尾。
  • 心跳：客户端定时发 {"t":"ping","n":N}，服务端回 pong。
  • 非法指令无副作用：未知 op 被静默忽略，不会踢连接——便于灰度加新指令。
  • 指令码 90+，覆盖面很广：战斗、市场、公会、房屋、家具、交易、宠物、镶嵌、精通、排队、投票、举报等。

5. 结论

API 状态：完全可用，且设计相当克制。

  • HTTP 层职责单一、语义清晰，/api/* 统一 JSON 约定。
  • 实时层是它真正的骨架：约 1.6 帧/秒的世界 tick + 视野内增量广播，实测 1266 人在线时单帧仅几百字节到十几 KB。
  • 鉴权边界清楚：无会话即 401，越权即拒绝，未发现明显信息泄露。
  • 值得注意的暴露面：/version.json 会直接吐出分支名与 commit（当前 dirty:true），等于对外公开构建进度——对一款在运营的游戏无伤大雅，但属于有意的"透明开发"策略。
