未知 ①　速度加成算法 —— 已完全还原

这是最关键的一项：利润面板要做到"每 tick 收益"，必须知道实际耗时怎么算。答案藏在 bundle 的一个复合函数里。

完整公式

勘误（本文档初版写反了）：`IT()` 是「每 tick 推进的进度」，不是耗时。 游戏代码里用的是它的倒数 1/Oh(t,o)，而 Oh = min(1, IT/baseTicks)。 所以 耗时 = baseTicks ÷ IT，而不是乘。初版写成乘法会让「等级越高越慢」，明显荒谬。 
// 实际耗时 = 基础耗时 ÷ (等级加成 × 工具系数 × (快捷+住处) × 精通系数)
function workTicks(you, action) {
  const speed = speedFactor(you, action);
  return action.baseTicks / speed;
}

function speedFactor(you, action) {
  return (1 + Math.max(0, level - action.levelReq) * 0.005)   // ① 等级加成
       * toolFactor(you, action)                              // ② 装备工具
       * combine(quickFactor, homeFactor)                     // ③ 特长 + 房屋
       * masteryFactor;                                       // ④ 精通
}

// 加成叠加法则：多个加成不是相乘，而是「各自减去 1 后相加」
function combine(...factors) {
  let sum = 0;
  for (const f of factors) sum += f - 1;
  return 1 + sum;
}

// 游戏里的进度判定（这也是判定语义的关键线索）
// Oh(action, you) = min(1, speed / baseTicks)        ← 每 tick 的完成概率
// if (roll(seed, id, tick, Oh(action, you))) complete()
已用真实数据实证：拿实测访客号的离线报告反推—— ticksApplied=329、产出 51 个铜矿、deposits=2、采矿 6 级无工具。 公式预测 50.9 个，实测 51 个，偏差 0.2%。 （其中还顺带标定出「背包满→跑银行」的往返耗时约 41 tick，这个值原来只能靠猜。）

四个因子的定义

因子公式数据来源
① 等级加成 1 + max(0, 当前等级 − 需求等级) × 0.005 存档 you.skills[skill] 与配方的 levelReq
② 工具系数 装备槽对应工具 → 1 + 该工具的品质加成 存档 you.equipment[pickaxe/rod/axe/…]
③ 快捷特长 1 + 0.005 × you.perks.quick 存档 you.perks.quick
③ 房屋加成 ∑ 已建造的 gatherSpeed/craftSpeed 房间加成 存档 you.house
④ 精通系数 1 + 精通等级加成（采集类取 gather，制作类取 craft） 存档 you.masteries
关键常数 0.005——即每超出需求等级 1 级，提速 0.5%。这个值是从游戏平衡配置对象里挖出来的（同处还定义了等级上限 99、基础经验 100、成长率 1.12）。

顺带还原：等级 / 经验曲线

maxLevel      = 99
baseXp        = 100
xpGrowth      = 1.12        // 每级经验需求 ×1.12
beyondGrowth  = 1.145       // 满级后每级 ×1.145

配套还找到了两个工具函数：等级→累计经验、经验→等级（二分查找）。这意味着"还需多少经验升级""这个行动每小时给多少经验"都能精确算出来。

未知 ②　市场协议 —— 已实测，并修正了此前判断

实测结果推翻了我上一份报告里的一个说法。四个市场指令的真实返回：

指令返回用途
marketBook {itemId, bid, bidQty, bidMore, ask, askQty, askMore, floor} 单品最优买卖价
marketBooks {tops:[ …同上，最多批量 } 批量拉多个物品的最优价
marketDepth {itemId, bids:[{price,qty}], asks:[{price,qty}], trades:[{price,qty,tick}]} 盘口深度 + 最近成交明细
marketHistory {rows:[…]} 你自己的成交记录（不是单品价格史）
修正：上一份报告我写"DVI 没有公开历史行情 API，历史要自己攒"——这个判断错了。marketDepth 直接返回 trades[] 数组，每笔带 price / qty / tick 时间戳。实测拿到 12 笔最近成交： 
"trades":[{"price":31,"qty":20054,"tick":39320525},
          {"price":31,"qty":11,   "tick":39319439},
          {"price":31,"qty":4,    "tick":39317003}, …]
所以行情类脚本可以立刻开工，不需要先攒几天数据——只是回溯深度有限（看起来是最近若干笔），长期曲线仍建议本地累积。
注意：marketHistory 用新访客号调用没有返回，因为那是"我的成交记录"——新号没有交易史。这也解释了为什么它不需要 itemId 参数。

另外确认：市场税率 marketTaxBp = 200，即 2%。算净利润时必须扣掉。

未知 ③　强化机制 —— 已完全还原

强化系统有一整套概率与费用模型，全部从 bundle 里还原出来了。

成功率

基础成功率 = max(0.2, 1 − 当前强化等级 × 0.06)      // 下限 20%
实际成功率 = min(1, 基础 × (1 + 藏书室加成) × 精通系数)
参数值含义
0.06每级衰减 6%+0 → 100%，+1 → 94%，+2 → 88% … 直到 +14 触底 20%
0.2成功率下限 20%再高的强化等级也不会低于两成
5最高强化等级存档里 Ys = 5
房屋「符文讲台」每级 +1% 成功率这是唯一的成功率增益来源

费用

金币 = 档位基数[强化档] × 品质倍率[物品品质] × (当前强化等级 + 1)
碎片 = 3 × (当前强化等级 + 1)     // 强化等级 ≥5 且使用核心时，碎片为 0

档位基数 = [100, 300, 1000, 3000, 8000, 20000]
品质倍率 = [1, 3, 8, 20, 50]

这意味着"把某件装备强化到 +N 的期望花费"是一个可精确计算的封闭式子——期望次数 = 1/成功率，乘上单次费用即可。强化类脚本的可行性从"需要实测采样"升级为"可以直接算"。

未知 ⑤　DOM 挂载点 —— 找到了 572 个稳定选择器

剩余待确认（次要）

  • 装备品质加成的具体数值表——工具系数里 1 + 品质加成 的那个"品质加成"还没有完整的数值表（物品表里只有 value，没有品质档位）。需要一个带装备的角色存档才能反推。
  • 精通加成的系数——精通因子函数已定位，但其内部数值表未完全展开。

这两项都只影响计算的精确度，不影响可行性——脚本可以先按无加成计算，或让用户手动校准。而且拿到一个真实玩家的存档后（就是写脚本时自然会有的东西），这两项都能立刻反推出来。

本报告基于公开客户端 bundle 的静态分析与公开接口的只读实测。逆向出的数值仅用于互操作性分析（计算玩家自己的收益、显示行情），不涉及对游戏状态的任何修改。
