Deep Vein Idle 脚本 —— 可行性测绘

依据：33 个 MilkyWayIdle 用户脚本的功能图谱 · DVI 公开 API 实测 · DVI 客户端 bundle 静态数据表提取

结论先说：DVI 能支撑的脚本比 MWI 更完整，而且在两个地方明显更强。它的 bundle 里直接内嵌了完整的游戏数据库，登录时服务端还会主动推送一份完整的离线收益报告——这两点让"利润计算"和"离线统计"类脚本几乎不需要逆向工作。

1. 数据资产盘点

写脚本的前提是知道数据在哪。DVI 的数据分三层，全部已实测确认：

第 1 层：静态数据库（内嵌在 bundle，一次抓取即可离线使用）

这是最有价值的发现。DVI 把整个游戏数值表打在前端包里，压缩变量解出来后是干净的 JSON：

表条目字段用途
物品表290id, name, stackable, value, heals基础价值 → 兜底定价、食物回血
配方表221id, name, skill, group, levelReq, baseTicks, xp, inputs[], output, grow, burn, bonus, caught利润计算的核心
怪物表20id, name, level, hp, maxHit, attack, defence, speed, xp, gold[lo,hi], bonus, drop战斗收益、掉落期望
经验曲线—dp[]升级进度、还需多少次
// 配方表样例：铁锭 = 1 铁矿 → 耗时 4 tick，经验 8
{id:42, name:"Iron bar", skill:"smithing", group:"Bars",
 levelReq:15, baseTicks:4, xp:8,
 inputs:[{itemId:3,qty:1}], output:{itemId:41,qty:1}}

// 怪物表样例：含金币区间与稀有掉落概率
{id:4, name:"Cairn wight", level:40, hp:75, maxHit:10, attack:40,
 defence:38, speed:4, xp:165, gold:[117,217],
 bonus:{itemId:204,chance:0.001}, drop:242}
注意：配方表里的 burn（烧焦）、caught（被抓住）、bonus（稀有额外产出）都是带概率的。这意味着"期望收益"可以算得比 MWI 更精确——MWI 的很多概率只能靠玩家实测统计。

第 2 层：实时增量（WebSocket 推送）

帧格式 {tick, m:[…], a}，约 1.6 帧/秒。已确认的消息类型：

消息载荷能支撑什么脚本
batch{kind:"produced", jobId, itemId, xp, tier, wire}产出统计、掉落追踪（对应 Better Loot Tracker）
work{siteId, tool, item}实时判断"我在做什么"，利润面板的输入
enter / leave{id, name, x, y, gear, mount, tag, title}在线名单、角色名片、社交功能
move{x, y, path[], speed}地图可视化、路线规划
chat{name, text, tick, channel, c}聊天增强、关键词提醒

第 3 层：按需拉取 + 服务端主动推送

数据来源内容
完整存档resync → snapshot.you79 字段：bank / pack / coins / gems / equipment(18槽) / skills(16) / plots / quests / perks / house / titles / masteries…
市场盘口marketBook / marketDepth{itemId, bid, bidQty, ask, askQty, floor}

2. 可行性矩阵

把 MWI 生态的功能逐项对到 DVI 上。可直接做 数据齐全；需补工作 部分数据要自建；不建议 有风险或无价值。

第一梯队 — 基础设施（其他一切的前提）

要写的模块对应 MWI依赖数据难点
DVI 核心库
DVICommon		 mooket + MWICommon 全部三层 WebSocket 分片重组（DVI 独有，MWI 没有这个问题）；建立共享命名空间与事件总线
静态数据包
DVIData		 MWITools 的内置表 第 1 层 已解决：三张表已提取成 JSON，可直接内嵌

核心库要做的事：「劫持 MessageEvent.data → 拼帧 → 遍历 m[] 按 .t 分派 → 派发 CustomEvent」。注意 DVI 与 MWI 的差异：MWI 一条消息一个 type，DVI 是一帧装多条消息，要循环。

第一梯队 — 数据与分析类

脚本对应 MWI实现要点
利润计算面板 MWI Profit Panel / AlchemyCalc 配方表给 inputs/output/baseTicks，市场给 bid/ask → 算每 tick 毛利、扣 marketTaxBp(200bp=2%) 得净利。还能算 xp/tick。这是对标 MWI 最核心的一个。
市场行情与历史 mooket / Market List History / Watch Market marketBook 轮询 + marketHistory 拉历史，本地 localStorage 攒时间序列，画折线/多日对比。注意：DVI 没有公开历史行情 API，历史要自己攒。
产出与掉落统计 Better Loot Tracker / 食用工具 监听 batch 消息累积产出；配合怪物表的 bonus.chance 算实际爆率 vs 理论爆率。
离线收益报告 食用工具·离线统计 直接读 welcome.offline，把 segments[] 渲染成表格/图表。成本最低、收益最直观。
每日资产曲线 Everyday Profit Plus / Pro 每日对 bank+pack+equipment+coins 按市场价估值快照，存本地，画净值曲线 + 分项（装备/库存/订单/房子/技能）变化图。
材料计算 + 购物清单 生产采集增强 / 市场伴侣 递归展开配方 inputs → 对比存档 bank/pack → 输出缺料清单并挂上市场价。MWI 的"一键购买"在 DVI 上不要做（见第 4 节）。
行动面板增强 ActionDetailPlus / MWITools 显示单次耗时、预计完成时间、还需多少次升级、当前 work 的实时进度。

第二梯队 — 可行但要额外投入

脚本对应 MWI缺什么
跨玩家行情服务 mooket 云端 / NiuMart / milkyway.market 需要自建后端 + 众筹数据。但 DVI 是单世界、在线仅 1266 人，市场规模比 MWI 小一到两个数量级——投入产出比要重新评估。
强化/精通统计 强化在线统计 / 康康运气 存档有 enhance / masteries / workRarity 字段，但强化概率机制不在静态表里，需要额外逆向或实测采样。
战斗收益分析 Better Loot Tracker 战斗部分 怪物表只有 20 条（等级 2–95），且 maxHit: 22 次说明另有少量未提取表。数据偏薄，不适合做战斗模拟器。
公会增强 食用工具·公会钉钉 指令齐全（guildInfo/Chat/Board/Rank/Donate/Deposit/Withdraw），数据也在 welcome 里，但要先摸清权限模型。

第三梯队 — 不建议

类型原因
自动操作类
自动采集 / 自动买料 / 自动收订单		 技术上完全可行（send 可拦截、指令明文可发），但——

3. 为什么"自动操作"是红线

DVI 的客户端内置了封禁机制——这是我在 bundle 里确认的： 
// WS 关闭码处理
if (code === 4001 || code === 4002) {
  this.closed = true;
  this.setState(code === 4002 ? "banned" : "elsewhere");
}
  • 4002 → "banned"：服务端可以主动封禁账号并强制断开，客户端有专门的状态 UI。
  • 4001 → "elsewhere"：异地登录检测。
  • 存档里还有 ironman 标志——说明官方在认真维护游戏完整性。

更关键的是这不是单机游戏：1266 人共享同一个世界，市场是零和博弈。自动化采集/交易会直接损害其他玩家的利益，也会让开发者针对脚本做对抗。MWI 生态里那些"一键购买""自动收订单"的功能，在 DVI 上应当明确排除。

可做的边界：只读分析、可视化、提醒、本地统计——所有不代替玩家做决策、不发送游戏指令的功能。这也恰好是 MWI 生态里最有价值的那一半。

4. 建议的实现顺序

阶段产出目的
P0 打通链路一个主题配色脚本验证 document-start 注入、DOM 观察是否可靠
P1 核心库DVICommon + 数据表分片重组、消息分派、事件总线、三张静态表内嵌
P2 最高性价比离线收益报告数据是服务端送的，一两天就能出成品，用来验证整条管线
P3 核心价值利润计算面板 + 市场行情记录对标 MWI 最核心的两个插件
P4 沉淀每日资产曲线 + 产出统计需要时间积累数据，但用户黏性最强

5. 还缺什么（写代码前要补的侦察）

  • 速度加成的计算方式——利润面板要精确到"每 tick 收益"，必须知道装备/等级/加成如何影响 baseTicks。这是目前最大的未知。
  • marketHistory 的返回结构和可回溯时间范围（决定行情脚本的天花板）。
  • 强化/精通的随机机制（若要写强化统计）。
  • 站点表（siteId → 地图坐标/工具/产出）——目前只在 work 消息里见过 siteId 数字，还没有 id→名称的映射，地图类脚本需要它。
  • DVI 的目标 DOM 结构——UI 挂载点需要实际打开页面确认（MWI 靠 .GamePage 类名和 React fiber，DVI 的渲染方式不同）。
本报告基于公开接口的只读探测与客户端 bundle 分析。提取出的数据表已存为 JSON： items.json (290) · actions.json (221) · monsters.json (20)，位于 dvi_probe/，可直接作为脚本的静态数据源。
