2. 核心技术机制

这是整份备份里最有价值的部分。这些脚本不修改游戏代码、也不替换 window.WebSocket，而是用三层"旁路"把自己挂进游戏的数据流。

第一层：劫持 MessageEvent.prototype.data 的 getter

游戏用 ws.onmessage = e => …e.data… 收包。既然每个 handler 都要读 e.data，那么给这个属性装个 getter，就能在游戏拿到数据之前截胡——而且游戏完全无感。

const oriGet = Object.getOwnPropertyDescriptor(MessageEvent.prototype, "data").get;

function hookedGet() {
  const socket = this.currentTarget;
  if (!(socket instanceof WebSocket)) return oriGet.call(this);
  if (!socket.url.includes("wss://api.milkywayidle")) return oriGet.call(this);
  const message = oriGet.call(this);
  Object.defineProperty(this, "data", { value: message });   // 防重入：同一条消息只派发一次
  try { dispatchEvent(new CustomEvent("MWI_" + JSON.parse(message).type, {detail: obj})); } catch {}
  return message;                                            // 原样交还给游戏
}
两个细节值得注意：
  • 防重入：一条消息可能被多个 onmessage 监听器读取。脚本用 defineProperty 把实例上的 data 换成固定值，确保 JSON 只解析一次、事件只派发一次。
  • URL 白名单：只对含 api.milkywayidle 的连接生效，避免污染站内其他 WebSocket。
  • Promise 微任务时机：部分脚本把处理逻辑塞进 new Promise(r=>r()).then(...)，把自身执行推迟到游戏 handler 之后，从而实现"后置钩子"。

第二层：劫持 WebSocket.prototype.send（可拦截发件）

Ranged Way Idle 走得更远——连发出去的包也能拦，靠一个 blockCurrentSendMessage 开关决定是否放行：

WebSocket.prototype.send = async function (message) {
  if (!this.url.includes("wss://api.milkywayidle")) return originalSend.call(this, message);
  globalVariables.blockCurrentSendMessage = false;
  globalVariables.webSocketMessageProcessor(message, 'send');   // 先给插件过一遍
  if (globalVariables.blockCurrentSendMessage) return;           // 插件可吞掉这条指令
  return originalSend.call(this, message);
};

它的配置项里甚至暴露了 debugPrintWSMessages、blockWSMessageByType——即"打印/屏蔽指定 type 的 WS 消息"，说明这套钩子是为深度调试设计的。

第三层：从 React Fiber 里掏出游戏对象

光有消息流还不够，要调用游戏自己的 API（打开市场、查询背包）就得拿到 React 组件实例。__reactFiber$ 是 React 挂在 DOM 节点上的内部属性，顺着它能爬到 stateNode：

window[injectSpace].game = (el =>
  el?.[Reflect.ownKeys(el).find(k => k.startsWith('__reactFiber$'))]?.return?.stateNode
)(document.querySelector('[class^="GamePage"]'));

共 6 个脚本用这招（市场伴侣、MWI_Toolkit、Ranged Way Idle、mooket 等）。代价是强耦合 React 内部实现——游戏一升级 React 或改类名就会失效。

7. 值得借鉴的工程手法

  • getter 劫持 > 替换构造函数：改 MessageEvent.prototype.data 比替换 window.WebSocket 隐蔽得多，不会破坏 instanceof 检查，也不与游戏自身的重连逻辑冲突。
  • 事件总线解耦：所有脚本统一用 CustomEvent("MWI_" + type) 派发，插件之间不需要互相引用——只要约定消息类型即可。这是可扩展的关键。
  • 防重入模式：Object.defineProperty(this, "data", {value}) 把自己换成定值，是处理"多处读取同一开销属性"的通用技巧。
  • 响应缓存 + 失效时间：MWICommon 把市场行情写进 localStorage 并记录 timestamp + 6h 作为失效点，避免每次刷新都重新拉取。
  • 配置驱动：300+ 条中英双语配置项集中管理，配合 debugPrintWSMessages 之类的调试开关，把"生产脚本"当"可观测系统"来做。
